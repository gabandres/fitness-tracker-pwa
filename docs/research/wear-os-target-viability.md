# Is a Wear OS complication worth building, and can it be tested where the iOS one cannot?

The question arrived from the owner, and the instinct behind it is sound enough
to be worth stating first: **the iOS watch surface has been undiagnosable for
eleven days because nothing but a physical wrist can exercise it.** If the
Android equivalent can be driven by an emulator, then the Android port is not
just parity — it is the first version of this feature that can have a regression
test at all.

That premise checks out. The costs are the problem.

---

## 1. The testability asymmetry is real, and it is the strongest argument for doing this

This is the part worth internalising, because it inverts the usual assumption
that iOS is the better-supported platform.

| | iOS + watchOS | Android + Wear OS |
|---|---|---|
| Maestro support | **Simulators only**, and no watchOS at all | **Emulators AND physical devices** |
| Watch driven by the test runner | No — no framework targets watchOS | **Yes** — a Wear OS emulator is an Android device over adb |
| Phone↔watch transport on a simulator/emulator | **Explicitly disabled by Apple** | **Documented as testable** |
| Complication reload observable in CI | No | Plausibly yes |

The middle row is the decisive one. Apple's own documentation states the watchOS
Simulator does not support `transferFile(_:metadata:)`, `transferUserInfo(_:)`
or `transferCurrentComplicationUserInfo(_:)`, and that physical devices should
always be used for Watch Connectivity transfers. `isComplicationEnabled` also
always returns `false` in the simulator. Those three APIs *are* the iOS watch
feature — `transferCurrentComplicationUserInfo` is the only queue that wakes a
sleeping watch app, and it is the entire subject of builds 44, 50 and 51.

So the iOS bug is not merely untested, it is **structurally untestable**, by
Maestro or XCUITest or anything else. That is not a gap in our suite and no
amount of test-writing closes it.

Google's position is the opposite: *"You can use the Wear OS emulator to test
your app's communication features"*, and Android Studio ships a **Wear OS
pairing assistant** that pairs a virtual watch with a virtual phone. Maestro
connects over adb and auto-detects running emulators, so a paired Wear emulator
is reachable by the same runner already driving `apps/mobile/.maestro/`.

**Caveat, stated honestly:** Maestro's Android docs never mention Wear OS,
minimum API levels, or non-phone form factors. The reasoning above is
*mechanical* — a Wear emulator speaks adb, Maestro speaks adb — not
documented. It is a one-hour spike to confirm, and it should be confirmed
before anything is scheduled on the strength of it.

## 2. What does not transfer from the iOS build

The iOS watch surface was cheap for one specific reason, and none of it applies here.

**`@bacons/apple-targets` globs `targets/_shared/*` into every target.** That is
what let `Glance.swift` — the snapshot contract, the staleness guard, the
strings table — exist once and compile into the phone app, the widget, the watch
app and the complication simultaneously. There is no Android equivalent. A Wear
module is a separate Gradle module producing a separate APK inside the same AAB,
and shared code has to be a real shared module or duplicated.

**The UI must be Kotlin.** Wear OS complications are
`ComplicationDataSourceService` implementations and Google's recommended path is
Jetpack Compose for Wear OS. `react-native-android-widget` — which draws our
Android home-screen widget inside our own JS context — does **not** cover Wear
OS. React Native cannot render a complication. This would be the first Kotlin UI
in the repo.

**The module has to be injected at prebuild.** `apps/mobile/android/` is
generated by CNG and gitignored, so a Wear module means a config plugin that
writes `settings.gradle`, a module `build.gradle`, and copies Kotlin sources —
the same shape as the existing `plugins/withGradleJvmArgs.js`, but considerably
larger. Signing config has to match the phone module's, or the pair will not
install together.

**The transport is a different API.** Wear OS uses the Wearable **Data Layer**
(`DataClient` / `MessageClient`), not WatchConnectivity. Two community modules
exist for the RN side — `react-native-wear-connectivity` and
`react-native-wear` — either of which would be the `modules/watch-link`
analogue. Neither provides the watch UI.

Note also: the Data Layer only works between an Android phone and a Wear OS
watch. A Wear watch paired to an iPhone gets nothing. That is fine here — it is
the Android app's feature — but it means the two platforms genuinely cannot
share a transport.

## 3. The timing risk: Tiles are being replaced this year

Google detailed **Wear Widgets replacing Tiles** in May 2026, and shipped the
first apps with support. Anything built against the Tiles API right now is
building on a surface mid-migration.

**Complications are not affected** and remain the correct target. This is a
reason to scope a v1 to *complications only* — which is also the exact analogue
of the iOS feature and the thing the owner actually wants on the wrist. A Tile
or Widget can follow once the dust settles.

## 4. What it would actually cost

Ordered by risk, not by effort:

1. **Config plugin injecting a Wear Gradle module** — the highest-risk item,
   because a broken prebuild breaks *all* Android builds, and the Mac is the
   only machine here that can compile Android at all.
2. **Kotlin complication data source + a minimal Wear app** — the app is
   required for the same App-Review-style reason as iOS: a complication tap has
   to land somewhere.
3. **Data Layer transport, phone side and watch side** — the `watch-link`
   equivalent, plus a listener service on the watch.
4. **Maestro flow against a paired emulator pair** — the payoff, and the thing
   that makes this different from the iOS build.
5. **Reusing `packages/core`'s snapshot contract** — the numbers and the
   staleness rule are already pure TS in `widget-snapshot.ts`; the Kotlin side
   needs a mirror the way `Glance.swift` is one. That is the drift risk to
   design against, and the reason the iOS side put it in exactly one file.

Realistically **one to two days**, against a few hours for most work in this
repo. It is not a "while we're here" item.

## 5. Recommendation

**Schedule it; do not start it now.** Three reasons, in order:

- **The iOS watch bug is open and two builds are in flight to diagnose it.**
  Starting a Kotlin Wear implementation now yields two unfinished watch
  surfaces, and this project's documented failure mode is exactly that — the
  reason `CLAUDE.md` carries the housekeeping rule about plan documents.
- **It does not help the open bug.** The emulator testability is a property of a
  *different feature on a different OS*. It is not a harness for the iOS
  transport and cannot become one.
- **The install base is currently zero.** Android is on the Play **alpha** track
  and has never launched. Nobody can receive this.

**When it is scheduled, the order that de-risks it:**

1. One-hour spike: pair a Wear emulator to a phone emulator and prove
   `maestro test` can drive the watch. **If that fails, the whole rationale
   collapses** and the decision should be revisited from scratch.
2. Complication only. No Tile, no Widget, until the Wear Widgets migration
   settles.
3. Mirror the snapshot contract from `packages/core`, one file, the way
   `Glance.swift` does — the drift this prevents is rendering yesterday's
   calories as today's, which is the most dangerous bug this feature class has.
