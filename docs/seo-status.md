# SEO status — baseline, 2026-07-29

**Why this file exists:** on 2026-07-29 the first-ever URL inspection of
ignia.fit found that **only the homepage was indexed**. Everything else — the
comparison pages, all 36 macro brackets, the calculator variants, the whole
Spanish half — was *unknown to Google*. That is the baseline every future
"did the SEO work?" question is measured against, and it existed nowhere but a
chat log.

Re-check any time with `node scripts/gsc.mjs inspect`.

---

## What was wrong

Three problems, discovered in this order, each hiding the next.

**1. There was no verified Search Console property for ignia.fit.** The account
owned `macrolog.web.app` (the Firebase default domain) and an unrelated site.
So every canonical on the site pointed at a domain Google had no property for,
and the sitemap had never been submitted anywhere that could receive it.
`public/google5e12a578f2d97eb3.html` had been sitting in the repo looking like
proof of verification; it verified the *other* domain.

**2. Nine URLs self-canonicalized to the homepage.** The eight calculator
variants and `/transformations` were listed in the sitemap but never
prerendered, so each served the SPA shell — homepage title, homepage
description, `canonical=https://ignia.fit/`. Nothing repaired it at runtime:
the app sets a title via `setTitleKey`, but no code anywhere writes a canonical
tag. Fixed 2026-07-29 by adding them to the prerender route table.

**3. The Spanish half did not exist as URLs at all** until 2026-07-28. The app
was fully translated; the site shipped 60 English URLs and zero Spanish ones.

**"Unknown" is not "rejected."** Google had never crawled these pages, so it
never judged them. The canonical bug was not suppressing rankings — there were
no rankings to suppress. Both matter now for the same reason: the pages are
about to be crawled for the first time, and they will be crawled correct.

## Still open

- **`sc-domain:ignia.fit` is unverified.** Needs a Cloudflare TXT record. Not
  required — the URL-prefix property is verified and sufficient — but the
  domain property covers `www`, both protocols and every subdomain in one
  place, which is the better long-term shape.
- **Request-indexing is manual.** There is no API for it: the Indexing API
  officially covers only `JobPosting` and `BroadcastEvent`, and pointing it at
  ordinary pages is outside its documented use. Give the sitemap a few days,
  then spend the daily quota on the pages worth ranking first — `/vs/*`,
  `/calculator`, `/es/calculator`.
- **`/download` and `/support` have no Spanish versions.** They are static HTML
  in `public/`, outside the prerender pipeline, so the Spanish funnel currently
  dead-ends in English at the conversion step.
- **`macrolog.web.app` is still a verified property serving the same content.**
  Every page there canonicalizes to ignia.fit, so it should not compete, but it
  is worth watching that Google does not index the `.web.app` host.

## How to check

```sh
node scripts/gsc.mjs status           # properties + verification state
node scripts/gsc.mjs submit-sitemap   # re-submit after a structural change
node scripts/gsc.mjs inspect          # the nine repaired URLs + a Spanish sample
node scripts/gsc.mjs inspect <url…>   # anything specific
```

Needs ADC with the `webmasters` and `siteverification` scopes — the command is
in the header of `scripts/gsc.mjs`. Keep `cloud-platform` in that list or the
firebase-admin scripts stop working.

**What to expect.** A newly submitted sitemap on a low-authority domain is
crawled over days to weeks, not hours, and discovery does not guarantee
indexing — thin or near-duplicate pages get crawled and dropped. The 36
`/macros/<goal>/<weight>-lb` pages are the most at risk of that, since they
differ mainly by number. If they are crawled and not indexed, that is a content
signal, not a technical one, and no amount of sitemap resubmission fixes it.
